# SysArch Studio：分层、分配与追溯使用说明（P1）

本文是 P1 规格书 §5 T9 第 2 步要求的交付文档，面向建模人员。内容包括：

1. 三层视图（SA / LA / PA）怎么用；
2. 分配怎么建；
3. 追溯怎么查，以及怎样同步到 Polarion；
4. 基线与差异、SysML v2 导出；
5. 验收方法和性能基线；
6. 已知限制。

元模型字段和视图的映射规则在 [`metamodel-and-views.md`](metamodel-and-views.md)，本文不重复。

| 入口 | 地址 |
|---|---|
| 建模（画布、属性、资源树、Validation 面板） | Sirius Web：`http://<主机>:8080` |
| 分配矩阵 / 追溯矩阵 | `http://<主机>:3000/?project=<项目>&table=allocation-matrix`，或 `table=requirement-trace` |
| 基线与差异 | `http://<主机>:3000/?project=<项目>&view=baselines` |
| 后端接口 | `/api/v1/...`，参见 `backend/src/main/resources/api/polarion-proxy.openapi.yaml` |

凡是需要 `<项目>` 的地方，都可以填三种值：Sirius 项目 id、Sirius 项目名称（名称必须唯一），或者在 `SYSARCH_POLARION_PROJECTS_<ID>` 里映射过的 Polarion 项目 id。

## 1. 三层视图怎么用

### 1.1 层是什么

每个元素都有 `layer` 字段。从上到下依次为 OPERATIONAL → SYSTEM → LOGICAL → PHYSICAL → EPBS。P1 为中间三层各提供一张视图：

| 视图 | 显示 | 新建工具 | 新元素的层 |
|---|---|---|---|
| 系统功能链（SA） | SYSTEM 层的块，以及它们之间的连接 | 新建功能 | SYSTEM |
| 逻辑架构（LA） | LOGICAL 层的块，以及它们之间的连接 | 新建逻辑组件 | LOGICAL |
| 物理架构（PA） | PHYSICAL 层的块，以及它们之间的连接 | 新建物理组件 | PHYSICAL |

### 1.2 打开视图

在 Sirius Web 的资源树里，右键一个块，选 **New representation**，然后选 SA、LA 或 PA。

- 视图显示的是**整份文档里本层的所有块**，与选哪个块作为根无关。如果作为根的块不在本层，它自己不会显示。
- 层过滤是视图的范围，**始终生效**，不能关掉，工具栏上也没有这个开关。如果想看别的层，请换一张视图。

### 1.3 在视图里建元素

1. 从画布空白处或块上打开工具板，选"新建逻辑组件"（另外两张视图里分别叫"新建功能"和"新建物理组件"）。
2. 工具会同时建两个元素：
   - 根块（或你点的块）下的一个 Part；
   - 一个同名、同层的块，作为这个 Part 的类型。
3. 新建的块马上出现在本视图里，切到其他层的视图则看不到。
4. 新元素的默认名称是 `partN`（见 §6），建好后请在画布上直接改名，或者在右侧属性里改。

### 1.4 连接

分层视图不画端口，所以**不能在这里拉连接**。具体做法：

1. 在 IBD 里，从源端口拖到目标端口。
2. 如果两端的接口不兼容，连接会被拒绝，两个端口标红。兼容的意思是：两端是同一个接口，或者一个沿 `superTypes` 是另一个的祖先。
3. 建好的连接会自动出现在 SA / LA / PA 里，画在两个端口所属部件的类型块之间，标签是接口名。

### 1.5 接口

接口是独立的元素（`InterfaceDef`，可以有协议、数据类型和父接口），端口和连接都引用它。新建接口的步骤：

1. 在资源树里新建一个 InterfaceDef。
2. 在端口属性的 Interface Type 里选中它。

没有填协议的接口，会在属性面板里标红"协议不能为空"。这只是提示，不会阻止保存。

## 2. 分配怎么建

分配（Allocate）表示"上层元素由下层元素实现"，**只能指向相邻的下一层**：

- SYSTEM → LOGICAL
- LOGICAL → PHYSICAL

### 2.1 在分配矩阵里建（推荐）

1. 打开 `:3000`，选择项目，选"分配矩阵"。
   - 行：SYSTEM、LOGICAL 两层的块和部件；
   - 列：LOGICAL、PHYSICAL 两层的块和部件。
   - 行和列都按层分组。
2. **点一下空格子**：建立"行 → 列"的分配，格子显示 ●。
3. **点一下有 ● 的格子**：取消这个分配。
4. 不合法的分配不会写入，页面顶部会显示原因，并高亮相关的行和列。例如：
   - `跨层跳过：SA → PA（跳过 LA）`：跳过了中间层；
   - `分配只能指向相邻的下一层：LA → LA`：同层分配，或者向上分配。
5. 矩阵每 10 秒刷新一次，页面重新获得焦点时也会刷新。所以别人在画布上做的修改，最多 10 秒后就会出现在矩阵里。

### 2.2 在资源树里建

也可以在资源树里新建 Allocate，再在属性里填 `from` 和 `to`。两端都填好之前，它只是"未完成"状态（`from`/`to` 标红），不算违规。两端填好后，如果违反相邻层规则，修改会被撤销，字段下方显示 `修改未保存：…`。

### 2.3 改层时的保护

如果把一个块的层改掉会让指向它的分配失效，这次修改会被撤销。例如把分配目标从 PHYSICAL 改成 EPBS，这样一个 LOGICAL → EPBS 的分配就跳过了 PHYSICAL 层。

## 3. 追溯怎么查

### 3.1 建立满足 / 验证关系

1. 打开 `:3000`，选择项目，选"需求追溯矩阵"。行是需求，列是 SYSTEM、LOGICAL、PHYSICAL 三层的块。
2. 点空格子，选"建立满足关系"或"建立验证关系"。格子显示 ○。
3. 点有 ○ 的格子，可以"取消满足关系 / 取消验证关系"，也可以补建另一种关系。

### 3.2 查追溯

- **页面**：就是上面的矩阵。
- **接口**：`GET /api/v1/trace/matrix?projectId=<项目>`，返回下面两部分：
  - 汇总：需求数、已满足、已验证、未满足；
  - 每条需求的 `satisfiedBy` / `verifiedBy`，包括元素 id、名称、类型和层。
- **缺口**：一致性报告（`GET /api/v1/consistency/report`）中，**R6** 列出没有任何满足关系的需求，级别 MINOR；已映射到 Polarion 的项目，Sirius 的 Validation 面板里也会列出。R6 不会自动修复，需要回到追溯矩阵里补上关系。

### 3.3 同步到 Polarion

前提：运维已经配置好 Polarion 地址，以及项目映射 `SYSARCH_POLARION_PROJECTS_<ID>`。

- **推送**：`POST /api/v1/sync/push`，需要以下内容：
  - 请求头 `Authorization: Bearer <你的 Polarion token>`；
  - 请求头 `Idempotency-Key`；
  - 请求体 `{projectId, elementIds[]}`。

  推送效果：
  - 满足关系写成 Polarion 原生链接 `implements`，验证关系写成 `verifies`，方向都是"满足者 → 需求"；
  - 推送一条需求时，会一并推送满足或验证它的元素，以及之前推送过的、指向它的链接。所以在模型里取消一条关系，下次推送就会从 Polarion 中删掉对应的链接。
  - 两端都必须已经绑定，或者在同一次推送里一起创建，否则报 `TRACE_TARGET_NOT_BOUND`。
- **拉取**：分手动和定时两种。
  - 手动拉取：`POST /api/v1/sync/pull`。
  - 定时拉取：配置了服务账号 `POLARION_SYNC_TOKEN` 后，每 15 分钟做一次增量拉取。
  - 拉取会写回以下内容：
    - Polarion 一侧拥有的字段：标题、需求正文，以及 reqId（等于 Work Item 编号）；
    - 已删除的 Work Item，标记为孤儿（R1）；
    - 在 Polarion 里被改动的模型字段或追溯链接，标记为冲突（CONFLICT）。冲突不会自动合并。
- **状态**：Validation 面板顶部有一行"上次推送 / 上次拉取 / 上次一致性校验"，以及定时任务的状态。
  - 连续失败 3 次后，定时任务暂停并显示红色告警，期间建模不受影响。
  - 手动拉取成功一次，或者调用 `POST /api/v1/sync/status/resume`，即可恢复。

## 4. 基线与导出

### 4.1 基线和差异

1. 打开 `:3000/?view=baselines`，选择项目，点"创建基线"。也可以调用 `POST /api/v1/baselines {projectId, label}`。基线是建立当时整个模型的快照。
2. 选一条基线，与"当前模型"或另一条基线比较，结果分三类：
   - 新增：只列元素 id；
   - 删除：只列元素 id；
   - 修改：列出元素 id，以及改动的字段，例如 `name`、`layer`、某个属性名。
3. 点新增或修改的行，会在 Sirius Web 里打开并选中该元素。

只改一个元素的名称时，差异只有 1 条修改。往块里加部件算 1 条新增，所属的块不会被算作修改。

### 4.2 SysML v2 文本导出

`POST /api/v1/export/sysmlv2`，请求体 `{projectId, scope, layer?, elementIds?}`，返回 UTF-8 文本。

| scope | 导出内容 |
|---|---|
| `PROJECT` | 整个项目 |
| `LAYER`（填 `layer`） | 本层的块、接口和需求；引用到的其他层定义只声明名称 |
| `ELEMENT`（填 `elementIds`） | 选中的元素；部件、端口和连接会带上它们所在的块 |

映射规则如下，SysML v2 没有对应语法的内容不会生造语法：

- 元素 id 写成短名 `<'PD-001'>`；
- `layer` 和 `stereotypes` 写成元数据 `@SysArchInfo`；
- 描述、需求字段、分配、满足/验证、ItemFlow 写成 `doc` 注释。

导出结果已经用 OMG SysML v2 试点实现校验过：无错误、无警告，解析得到的元素数和名称与模型一致。在 SysON 里导入（P1-AC-5）还待确认。

## 5. 验收和性能基线

### 5.1 一键验收脚本

后端运行起来以后，执行：

```bash
node tests/acceptance/p1-acceptance.mjs [http://localhost:8080] [--keep]
```

脚本用演示模板建一个临时项目，依次检查下面几项，结束后删除这个项目（加 `--keep` 则保留）。需要 Node 22 或更高版本，无其他依赖。

| 检查 | 内容 |
|---|---|
| AC-7 / P0 AC-1 | 健康检查返回 UP |
| P1-AC-1 | LA 只显示 4 个 LOGICAL 块；在 LA 新建的元素是 LOGICAL，在 PA 不可见 |
| P1-AC-2 | 在分配矩阵里建 SA → PA，返回 422，提示 `跨层跳过：SA → PA（跳过 LA）` |
| P1-AC-3（模型侧） | 在追溯矩阵里建立满足关系后，格子有标记，`/trace/matrix` 中该需求变为已满足 |
| P1-AC-4 | 建基线后在画布上改一个名称，差异恰好是 1 条修改 `[name]` |
| AC-7 / P0 约束 | LA → LA 的分配被拒 |

脚本测不到的部分，覆盖方式如下：

- P1-AC-3 的 Polarion 侧和 P1-AC-6：会写 Polarion，由 `TraceAndScheduleIT`（WireMock）覆盖，T6 时又对本机 Polarion 2512 做过实测；
- P1-AC-5：需要 SysON；
- P0 AC-2～AC-6 中只能在浏览器里看的部分：P0 验收时已在浏览器检查；对应的自动化测试每次构建都会跑。

删除项目时，它的基线不会跟着删除（试用问题 T9-02），所以每跑一次脚本，`baseline` 表里会多一条 `p1-acceptance` 记录。

### 5.2 性能基线：500 个元素，三张视图同时打开，切换视图 < 1 s

| 测量 | 方法 | 结果（2026-11-09，本机） |
|---|---|---|
| 服务端渲染（CI 门禁） | `ViewSwitchPerfTest`：500 个元素，SA/LA/PA 轮流各渲染 120 次；一半是模型没变时的切换，一半是先改名再切换 | 中位数 3～5 ms，最慢 10～22 ms（两次运行） |
| GraphQL 端到端 | 上传同一份 500 元素文档，三张视图保持订阅，再订阅目标视图，直到收到完整的图（45 次） | 中位数 8 ms，最慢 14 ms |
| 浏览器（Sirius Web） | 三个标签页都打开，点击标签，直到目标层的 31 个节点都进入 DOM（30 次） | 中位数 605 ms，P95 684 ms，最慢 708 ms |
| 三张视图都开着时编辑一次 | 用分配矩阵建一条分配，直到三张视图都收到刷新（10 次） | 中位数 103 ms，最慢 193 ms |

说明：

- 测试模型共 500 个元素：每层 1 个根块、30 个类型块、30 个部件、60 个端口、29 条连接；另有 1 个接口和 49 条分配。
- 浏览器的结果达标，但余量不大。时间主要花在 Sirius 前端重新挂载画布、做布局和适配视口上，服务端只占约 1%。如果客户端机器比本机慢，需要复测。
- CI 门禁 3（`checkPerfThreshold`）在原有刷新阈值之外，增加了"任何一次切换 ≥ 1000 ms 即失败"。

## 6. 已知限制

| 限制 | 影响 | 办法 |
|---|---|---|
| 分层视图里不能拉连接 | 连接只能在 IBD 里建 | 设计如此：分层视图不画端口 |
| `spline` 连线画成直线 | 仅影响外观 | Sirius 2025.8 不支持曲线 |
| 分层视图新建元素的默认名称是 `partN` | 需要手动改名 | 试用问题 T9-03，未修 |
| 删除 Sirius 项目后，基线仍留在库里 | 通过接口查不到（项目已不存在），只占空间 | 试用问题 T9-02，未修 |
| 未绑定池里的 Work Item 不能认领 | OpenAPI 里没有认领接口 | 留待 P2 |
| Polarion 没有内置的出站 webhook | `/webhooks/polarion` 要靠 Polarion 侧的扩展来调用 | 依靠定时增量拉取 |
| 表格页面不在 Sirius 界面里 | 矩阵要在 `:3000` 打开 | 前端外壳挂载 Sirius 组件之前都是这样 |
