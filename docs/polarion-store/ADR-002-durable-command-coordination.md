# ADR 002 以持久执行闸门限制同模型并发事务

状态：最小探针已实测通过，未用于正式模型服务。

真实探针已证实：两个并发事务均通过 expectedVersion 检查后，落败事务停在 Polarion SVN 驱动的 `JavaSvnDriver.delayBeforeCommitRestart`，60 秒内不返回。SDK 的原子回滚可用，但它本身不足以提供本应用所需的有界冲突语义。

新增 SysMLTool 自身 PostgreSQL 中的持久命令闸门，仅保存模型键、请求／命令 ID、主体和 ACTIVE／UNKNOWN 状态。它不保存模型，且不连接 Polarion 数据库。Polarion SDK 仍负责模型的原子提交和权限。

以数据库唯一约束原子取得模型执行资格，竞争者立即返回 409。资格取得使用独立自动提交语句，在调用 Polarion 前完成，不持有跨网络的数据库事务或 Java 内存锁。多个服务进程或实例必须共享同一个协调库。

成功提交或已确认回滚后才能移除自己的资格。提交结果不明时保留 UNKNOWN，不依靠自动租约过期开放下一次写入。服务进程重启、连接失效不自动删除资格；恢复需要查询 Polarion 的持久命令结果并核对原请求。

该设计依赖正式模型所有写入口统一经过命令服务，且托管字段的原生编辑受保护或可检测漂移；这些仍是 M3／M4 的必要条件。它不能宣称 Polarion 原生 SVN 重试已经修复，也不能解决未受控外部写入或全部模型历史恢复。

M0 仅在 `sysarch_probe_m0.command_gate` 中验证机制，连接配置保存在受限 `build/private/` 文件，不放入 JAR、命令行或 Polarion 启动属性。失败时不回退到裸 SDK 并发写入。21 项真实核心检查及 4 项跨进程数据库检查通过，包含 UNKNOWN 的显式恢复，见 [验收报告](M0-live-acceptance-2026-11-18.md)。

正式启用仍需处理字段保护、进程强杀后的 ACTIVE 孤儿资格、协调库丢失及重建。协调库不能重建为空表后立即开放写入，必须先核对 Polarion 的持久提交结果和未决请求。当前恢复测试不等同于所有崩溃和网络分区场景通过。
